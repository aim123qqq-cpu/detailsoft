# DetailFlow

Рабочий mobile-first поток CRM: клиент и автомобиль, каталог услуг, запись, приёмка, версионная смета, согласование, работы мастера, выдача и закрытие заказа.

## Запуск

Требуется Node.js 24+ и pnpm 11+.

```powershell
pnpm install
pnpm dev
```

Интерфейс откроется на `http://127.0.0.1:5173`. Для production-проверки:

```powershell
pnpm build
pnpm start
```

Приложение будет доступно на `http://127.0.0.1:4173`.

Демо-поиск: `+7 913 123-45-67`. У клиента есть Mazda 3 BL и Toyota Camry XV70.

Лендинг продукта — статическая страница `public/landing/index.html`, после сборки она доступна на `/landing/` рядом с приложением. Скриншоты для неё (`public/landing/img`) снимаются с демо-данных: `pnpm build`, затем `node scripts/landing-shots.mjs`.

Вторая версия лендинга — `public/landing22/` (`/landing22/`): на первом экране работает настоящая схема приёмки. Её геометрия берётся из `src/shared/carLayouts.ts` скриптом `node scripts/landing-layouts.mjs` (запускать после изменения схем). Кнопка в конце страницы открывает приложение с номером в поиске: `/?phone=…` или `/?plate=…`.

## Архитектура инкремента

- `migrations/001_customer_vehicle.sql` — tenant-scoped Customer/Vehicle модель. `Customer` и `Vehicle` разделены временной связью `CustomerVehicle`; госномер намеренно не имеет жёсткого `UNIQUE`.
- `migrations/002_booking_services.sql` — услуги, операции, пакеты, классовые цены, записи и снимки предварительного расчёта.
- `migrations/003_order_intake_estimates.sql` — рабочий заказ, структурированная приёмка, неизменяемые версии сметы, решения клиента и аудит.
- `migrations/004_order_production_qc.sql` — назначение мастера, снимок согласованных операций и паузы; таблицы QC сохранены для совместимости.
- `migrations/005_order_delivery_payments.sql` и `006_retire_order_payments.sql` — выдача и закрытие заказа; ранний платёжный прототип архивирован и исключён из продукта.
- `migrations/009_leads.sql` — tenant-scoped очередь обращений и отдельная связь конвертированного обращения с записью.
- `migrations/010_center_settings.sql` — рабочие дни, часы, шаг слотов и одновременная вместимость центра без обязательных боксов.
- `migrations/011_team.sql` — сотрудники tenant, совмещаемые роли, блокировка доступа и хешированные локальные токены входа.
- `migrations/012_vehicle_history.sql` — аудит смены владельца и статуса автомобиля без перезаписи исторических заказов.
- `migrations/013_reference_management.sql` — tenant-override тарификационного класса ручных и справочных автомобилей.
- `migrations/014_customer_audit.sql` — append-only журнал карточки клиента: изменение контактов, архивация и возврат из архива.
- `migrations/015_booking_quote_versions.sql` — неизменяемые версии состава записи; исходный снимок `booking_quote_lines` не переписывается.
- `migrations/016_order_documents.sql` — номерные неизменяемые акты приёмки и выдачи с необязательной подписью клиента.
- `migrations/018_order_assignment_members.sql` — связь назначения мастера с реальным сотрудником; имя в заказе остаётся снимком.
- `migrations/022_booking_slot_conflicts.sql` — пометка «конфликт времени» у записи, сделанной без сети, пока её не перенесут.
- `migrations/023_order_intake_body_types.sql` — тип кузова, выбранный при приёмке: по нему строится схема осмотра с нумерацией элементов (`src/shared/carLayouts.ts`).
- `migrations/021_idempotent_requests.sql` — запомненные ответы на изменения с `Idempotency-Key` для отправки очереди без сети.
- `migrations/020_catalog_sections.sql` — разделы каталога и их порядок; цена по умолчанию хранится строкой с классом `*`.
- `migrations/019_tenant_roles.sql` — настраиваемые роли центра (права системных ролей и свои роли) и журнал их изменений.
- `migrations/017_messenger_auth.sql` — вход сотрудников через бота: привязки мессенджеров, приглашения, запросы входа и сессии (только хеши секретов).
- `server/messenger/` — адаптеры Telegram и MAX (long polling) и общий диалог бота; `server/auth-repository.mjs` — приглашения, вход и сессии.
- `server/` — HTTP API на стандартных модулях Node.js и встроенном `node:sqlite`. Tenant определяется сервером из bearer-сессии, а не из заголовка, выбранного клиентом.
- `src/` — React mobile UI с полным переходом от обращения и поиска клиента до автомобиля, готового к выдаче, ручным вводом авто, календарём, рабочими заказами, карточками клиента и автомобиля, историей владельцев и конструкторами каталога, графика и команды.
- `tests/` — модульные, API-интеграционные и Chromium end-to-end проверки полного потока до статуса `CLOSED`, истории автомобиля, карточки клиента и конструктора каталога.

### Вход сотрудников через Telegram или MAX

Сотрудник входит без пароля: подтверждает вход в боте мессенджера, к которому его привязал владелец центра. Боты бесплатны, а сервер получает сообщения методом long polling, поэтому публичный домен не нужен.

1. Создайте бота: в Telegram через [@BotFather](https://t.me/BotFather) (`/newbot`), в MAX — в кабинете business.max.ru → «Чат-боты». Скопируйте токен.
2. Скопируйте `.env.example` в `.env` (файл не попадает в git), впишите токен в `TELEGRAM_BOT_TOKEN=` и/или `MAX_BOT_TOKEN=` и запустите DetailFlow:

   ```powershell
   pnpm start          # или: node --env-file-if-exists=.env server/index.mjs
   ```

   Не пересылайте токен в чаты и тикеты: тот, у кого он есть, управляет ботом. Если токен утёк, перевыпустите его в @BotFather (`/mybots` → API Token → Revoke).

3. В «Профиль → Команда» откройте сотрудника и нажмите «Пригласить в Telegram» или «в MAX». Отправьте ссылку сотруднику: он откроет её и нажмёт «Старт».
4. Если на сервере настроен хотя бы один бот, DetailFlow открывается на экране входа. Сотрудник выбирает мессенджер, открывает бота (или отправляет ему код с экрана) и подтверждает вход кнопкой. Код на экране и в боте должен совпадать.

Пока демо-доступ разрешён, на экране входа есть кнопка «Продолжить в демо-режиме»: выбор запоминается до закрытия вкладки. `DEMO_AUTH=false` на сервере убирает её полностью. Без настроенных ботов приложение, как раньше, сразу открывается в демо-режиме. Контракт описан в [docs/API.md](docs/API.md#контракт-входа-через-мессенджер).

### Поделиться сметой после выдачи

У закрытого заказа (экран «Заказ закрыт» и детали в разделе «Заказы») есть кнопка «Поделиться сметой». Она открывает штатное меню «Поделиться» телефона с готовым текстом: центр, автомобиль, выполненные работы, итог по согласованной смете и дата выдачи. Телефона клиента и сведений об оплате в тексте нет. Отправить могут администратор или мастер через любое приложение: WhatsApp, Telegram, SMS. Меню «Поделиться» и буфер обмена браузер даёт только по HTTPS или на `localhost`. По адресу вида `http://192.168…` текст откроется для ручного копирования.

Согласование сметы при приёмке остаётся голосовым: администратор фиксирует его способом «Лично» или «Телефон» с ответственным.

### Акты приёмки и выдачи

После сохранения приёмки можно оформить «Акт приёмки», после закрытия заказа — «Акт выдачи (заказ-наряд)». Сделать это можно на шаге сметы, на экране закрытого заказа или в деталях заказа в разделе «Заказы». Клиент видит документ до сохранения и может подписать его пальцем на экране. Можно сформировать акт и без подписи, чтобы подписать на бумаге. Каждый акт получает номер и больше не меняется. Если приёмку осмотрели заново, прежний акт помечается «устарел» и остаётся в истории. Кнопка «Печать / PDF» выводит только документ. Подпись необязательна и не блокирует работу.

### Рабочая установка

Как поставить DetailFlow без демо-доступа, создать первого владельца (`pnpm setup:owner`), обновить, откатить и включить HTTPS, описано в [docs/DEPLOY.md](docs/DEPLOY.md). Там же адреса проверки `/api/health` и `/api/ready` и все переменные окружения.

### Android-приложение (тестовая сборка)

`android/` — оболочка на системном WebView без сторонних библиотек. Интерфейс и данные по-прежнему отдаёт сервер DetailFlow; приложение при первом запуске спрашивает его адрес (позже его можно сменить в «Профиль → Сервер»). Ссылки на бота открываются в Telegram/MAX, «Поделиться», печать актов и копирование идут через Android, кнопка фото открывает камеру. Фото с камеры сохраняются и в галерее, в папке `Pictures/DetailFlow`.

Сборка (нужен Android Studio: из него берутся JDK и SDK):

```powershell
$env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"
cd android
.\gradlew.bat assembleDebug -PdetailflowServer=http://192.168.1.60:4173   # адрес подставится в поле при первом запуске
# APK: android\app\build\outputs\apk\debug\app-debug.apk
```

Чтобы телефон достучался до сервера, запустите его на всех интерфейсах и держите телефон в той же сети Wi-Fi:

```powershell
$env:HOST = "0.0.0.0"; pnpm start
```

С `HOST=0.0.0.0` и включённым демо-доступом DetailFlow доступен любому устройству в этой сети. Для проверки дома это нормально, в центре лучше поставить `DEMO_AUTH=false`.

Установка: `adb install -r app-debug.apk` по USB с включённой отладкой или передайте файл на телефон и разрешите установку из этого источника. Сборка debug подписана отладочным ключом и предназначена только для проверки.

Проверка на эмуляторе или телефоне: откройте приложение, подключитесь к серверу и выполните `node tests/android/smoke.mjs`. Скрипт через Playwright управляет настоящим WebView: создаёт запись в демо-центре, проверяет «Сервер» в профиле и системное меню «Поделиться».

### Резервные копии

Все данные центра хранятся в одном файле `data/detailflow.db`. DetailFlow копирует его сам:
- при каждом запуске — до применения миграций, поэтому неудачное обновление всегда можно откатить;
- раз в сутки, пока сервер работает (`BACKUP_INTERVAL_HOURS`, по умолчанию 24).

Хранятся последние 14 копий (`BACKUP_KEEP`) в папке `data/backups/`. Используется онлайн-копирование SQLite, поэтому копия согласована даже во время записи.

```powershell
pnpm backup                 # копия прямо сейчас
pnpm backup -- --list       # список копий
pnpm restore -- data/backups/detailflow-20261016-100000-daily.db
```

Восстановление работает только при остановленном сервере. Файл копии проверяется на целостность, а текущая база перед заменой сама сохраняется в копию `…-before-restore.db`, так что восстановление можно отменить. Копии лучше регулярно переносить на другой диск или в облако: если откажет диск компьютера, копии на нём пропадут вместе с базой.

### Рабочее место по роли

Интерфейс подстраивается под роль сотрудника:
- **Мастер** открывает приложение на «Заказах» с фильтром «Мои» — заказы, где он назначен исполнителем.
- **Приёмщик** открывает приложение на «Записях»: может начать приёмку, но не видит обращений, переноса и отмены.
- **Администратор** назначает мастера из реального списка команды; у каждого мастера показано, сколько у него заказов в работе.

Нижняя навигация не меняется. Раздел, недоступный роли, показывает понятное сообщение вместо ошибки. Телефоны и обращения сервер отдаёт только ролям, которым они нужны.

### Роли и права

Владелец настраивает доступ в «Профиль → Команда → Роли и права»:
- у Администратора, Приёмщика и Мастера можно изменить набор прав;
- можно создать свою роль (например, «Старший мастер») и отметить ей права галочками из 11 пунктов;
- сотрудник может совмещать несколько ролей.

Правка роли сразу действует для всех её сотрудников, каждое изменение записывается в журнал. Владелец всегда имеет полный доступ, и только он управляет командой. Если владелец сам выполняет работы, ему дополнительно назначают Мастера: в список исполнителей попадают только сотрудники с правом «Исполнитель заказов». Роль, которая есть хотя бы у одного сотрудника, нельзя отправить в архив. Контракт описан в [docs/API.md](docs/API.md#контракт-ролей).

### Запись заранее: приезд, неявка и продолжение заказа

В деталях подтверждённой записи («Записи → запись») есть кнопка «Клиент приехал — начать приёмку». Она открывает рабочий экран заказа поверх раздела. После времени начала появляется «Клиент не приехал»: запись получает статус «Не приехал» и освобождает слот. Начатый заказ открывается кнопкой «Открыть рабочий заказ» в записи или «Продолжить работу с заказом» в разделе «Заказы», с того этапа, на котором он остановился. Это работает и для мастера. После возврата списки обновляются.

### Работа без сети

Приложение хранит на телефоне копию всего, что сотрудник открывал: списки, записи, заказы, карточки, каталог. Незакрытые заказы из списка «Заказы» (до 30) сохраняются в фоне вместе с их записями, поэтому мастер может открыть заказ, даже если не заходил в него при связи.

Если сервер недоступен, вверху появляется «Нет подключения». Экраны открываются из копии, а работу по заказу можно продолжать:
- приёмка и фото;
- начало работ и отметки операций;
- пауза и её снятие;
- завершение работ.

Действия применяются к копии заказа по тем же правилам, что на сервере, и встают в очередь. Когда связь появляется, очередь уходит по порядку. Повторная отправка не выполняет действие дважды. Если сервер отклонил изменение (например, заказ за это время изменили с другого телефона), плашка покажет, какое именно и почему, с кнопками «Повторить» и «Отменить изменение». Отмена снимает это изменение и следующие по тому же заказу, а заказ перечитывается с сервера.

Android-приложение сохраняет файлы интерфейса у себя и запускается даже при выключенном сервере. В обычном браузере по адресу `http://192.168…` без сети работает уже открытая вкладка, а новый запуск без сервера потребует HTTPS.

**Записи без сети.** Администратор может найти клиента по телефону или номеру, выбрать услуги, увидеть стоимость и свободное время и записать клиента. Перенести запись тоже можно. Для этого приложение держит на телефоне график, цены, занятость на 90 дней вперёд и клиентов с машинами, обновляет их раз в 10 минут и после каждой записи. Свободное время и стоимость телефон считает тем же кодом, что сервер.

Запись без сети сохраняется на телефоне с пометкой «Не отправлено» и уходит, когда появится связь. Если это время за это время заняли с другого телефона, запись не пропадёт: сервер сохранит её с пометкой «Конфликт времени», и её нужно перенести. Перенос без сети, который не прошёл из-за занятого времени, покажется в плашке как «не отправлено», а запись останется в прежнем времени.

**Весь визит без сети.** По записи можно нажать «Клиент приехал — начать приёмку» и без связи пройти всё до выдачи:
- приёмка и фото;
- смета и согласование;
- назначение мастера;
- работы;
- фото результата и выдача.

Записи на сегодня и завтра и список мастеров телефон сохраняет заранее. Номера заказа и сметы выбирает телефон, поэтому все шаги ссылаются друг на друга и после отправки совпадают с сервером. Отменить запись и отметить неявку без сети тоже можно: время освобождается сразу. Если по этой же записи приёмку уже начали на другом устройстве, сервер откажет, и плашка покажет это изменение как «не отправлено». Акты приёмки и выдачи формируются только при связи: их содержимое собирает сервер.

**Акты без сети.** Акт приёмки или выдачи можно показать клиенту и подписать без связи. Номер акт получит, когда дойдёт до сервера. До этого на нём написано «номер присвоится при отправке».

**Сохранённая копия не растёт бесконечно.** При связи с сервером, при запуске и раз в 6 часов приложение удаляет:
- закрытые заказы и завершённые записи через 2 дня;
- любые заказы и записи через 21 день;
- старые поиски и списки через 7 дней;
- копии других сотрудников на этом телефоне через 7 дней;
- самое старое сверх 80 МБ.

То, что ждёт отправки, и данные для записи без сети не удаляются никогда.

Плашка сети стоит над заголовком экрана и сдвигает содержимое вниз, а не закрывает его.

**Новые клиенты и автомобили без сети.** Нового клиента, его машину (из справочника, если он сохранён, или вручную) и запись можно завести без связи. Телефон сразу проверяет дубли по сохранённым данным: тот же номер телефона или тот же госномер.

Если пока телефон был без сети, этот номер телефона уже завели с другого устройства, при отправке появится вопрос:
- «Это <имя>» — машина и запись привязываются к уже существующему клиенту, второй клиент не создаётся;
- «Это другой человек» — клиент создаётся с явным подтверждением.

Клиенты на сервере никогда не объединяются. Если отменить создание клиента, вместе с ним отменятся и его машина, запись и заказ, сделанные без сети.

### Каталог услуг

«Профиль → Каталог» разбит на разделы, например «Мойка и уход» или «Салон». Разделы можно создавать, переименовывать, менять местами и удалять, если они пустые. В этом же порядке разделы показываются при записи.

Услуга заводится одной формой: раздел, название, время и цена. Если для разных классов авто цена и время отличаются, их задают по классам. Незаполненные классы берут основную цену. Сложные услуги по-прежнему можно собрать из нескольких операций кнопкой «Собрать услугу из нескольких операций». Пакеты и библиотека операций остались без изменений. Изменение цен влияет только на новые расчёты. Контракт описан в [docs/API.md](docs/API.md#контракт-разделов-и-простых-услуг).

### Изменение состава записи

В деталях подтверждённой записи без заказа есть кнопка «Изменить состав». Она открывает тот же каталог услуг, затем показывает сравнение «было/станет». После сохранения создаётся новая версия расчёта (v2, v3…), предыдущие видны в «Истории расчёта». Цены считает сервер. Если новая длительность не помещается в выбранное время, прямо на экране сравнения появляется выбор даты и времени под новую длительность. Кнопка «Сохранить и перенести» меняет состав и время одним действием. После создания заказа состав меняется только через смету.

### Карточка клиента

Открывается из результата поиска по телефону и госномеру, обращения, записи, заказа и из владельца в карточке автомобиля. Показывает контакты, текущие, неактивные и прежние автомобили, записи, заказы и журнал изменений. Изменение телефона, который уже есть у другого клиента центра, требует явного подтверждения: клиенты не объединяются, автомобили не переносятся. Архивация — отдельное действие. Она недоступна, пока есть подтверждённые записи, незакрытые заказы или активные обращения, и не меняет историю. Архивный клиент находится поиском по телефону с пометкой «архив» и возвращается кнопкой «Вернуть из архива». Контракт описан в [docs/API.md](docs/API.md#контракт-карточки-клиента).
- `artifacts/` — локальные скриншоты реального e2e-прохождения; в Git не добавляются.

Демо-токены нужны только для локального прототипа. Перед production-развёртыванием их следует заменить существующей системой аутентификации и авторизации.

### Депрекация QC

Обязательный этап QC заморожен: новые заказы после выполнения всех операций сразу переходят в `READY`. Исторические проверки и backend-реализация сохранены. Для временного rollback нужно одновременно запустить сервер с `ENABLE_QC=true` и собрать клиент с `VITE_ENABLE_QC=true`. Удаление таблиц и исторических данных не планируется до отдельного решения.

## Проверки

```powershell
pnpm check        # сборка, затем все тесты (E2E открывают собранный dist/)
pnpm test:e2e     # только Chromium E2E
```

E2E используют установленный Google Chrome; другой путь задаётся переменной `CHROME_PATH`. Те же проверки GitHub Actions запускает на каждый push (`.github/workflows/ci.yml`).

API-контракт описан в [docs/API.md](docs/API.md).
