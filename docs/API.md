# API — реализованные итерации

Все маршруты `/api/*`, кроме `/api/health`, `/api/ready` и публичных маршрутов входа `/api/auth/providers` и `/api/auth/login-requests…`, требуют `Authorization: Bearer <session-token>`. Tenant извлекается из серверной сессии; переданный клиентом `x-tenant-id` не определяет область данных. Принимаются три вида токенов:

- сессия входа через мессенджер (`dfs_…`, см. «Контракт входа через мессенджер»);
- код доступа сотрудника из раздела «Команда»;
- демо-токены локальной версии. Они отключаются переменной `DEMO_AUTH=false`.

Некорректный JSON в теле запроса возвращает `400 invalid_json`.

**Повтор изменений.** Изменяющий запрос (не `GET`) можно отправить с заголовком `Idempotency-Key`. Сервер запоминает первый ответ на 7 дней отдельно для каждого центра. Повтор с тем же методом, путём и телом получает этот ответ (с заголовком `idempotent-replay: true`), и изменение второй раз не выполняется. Тот же ключ с другим запросом — `409 idempotency_conflict`. Запоминаются все ответы, кроме `5xx` и `401`, так что отказ при повторе тоже повторяется. Так приложение отправляет очередь изменений, сделанных без сети (таблица `api_idempotent_requests`, миграция `021`). У создания записи свой механизм ключа.

**Кэш.** Ответы API отдаются с `Cache-Control: no-store`: копию данных для работы без сети приложение хранит само. Файлы сборки `/assets/*` кэшируются навсегда, `index.html` — с `no-cache`.

**Записи без сети.** `GET /api/offline/booking-pack` (право `manageBookings`) отдаёт всё, что нужно телефону, чтобы сделать или перенести запись без сервера:
- `schedule` — график центра;
- `sectionOrder` — порядок разделов;
- `packages` и `services` — цены и время по классам (`'*'` — цена по умолчанию);
- `busy` — подтверждённые записи с прошлых суток;
- `customers` и `vehicleClasses` — клиенты с машинами и класс каждой машины. Только при праве `manageCustomers`, иначе пустые.

Свободное время, расчёт, каталог для машины и подпись цены и сервер, и приложение считают одним кодом — `src/shared/bookingRules.ts`, нормализацию телефона и номера — `src/shared/normalize.ts`. Сервер импортирует эти `.ts` напрямую (Node 24).

`POST /api/bookings` дополнительно принимает:
- `id` — номер, выбранный телефоном, в формате `booking_<uuid>`. Неверный формат — `422`, занятый номер — `409 booking_exists`;
- `allowSlotConflict: true` — запись из очереди без сети сохраняется, даже если её время заняли, но с пометкой.

Пометка хранится в `booking_slot_conflicts` (миграция `022`) и видна как `slotConflict: true` в записи и списках. Перенос на свободное время или отмена снимают её. Без `allowSlotConflict` занятое время по-прежнему даёт `409 slot_unavailable`.

**Номера от телефона для заказа и сметы.** Чтобы заказ, начатый без сети, мог дойти до выдачи, номера выбирает телефон:
- `POST /api/orders` принимает `id` (`order_<uuid>`). Если по этой записи приёмку уже начали с другим номером — `409 order_exists_for_booking`; тот же номер — повтор.
- `POST /api/orders/{id}/estimates` принимает `id` версии (`estimate_<uuid>`) и `id` строк (`estimate_line_<uuid>`). Неверный формат или повтор номера внутри сметы — `422`, уже занятый номер — `409 estimate_exists`.

От этих номеров зависят согласование (`estimateVersionId`) и операции работ.

**Операции работ** при старте получают номер `work_operation_<id строки сметы>`. Телефон, начавший работы без сети, вычисляет те же номера, и отметки из очереди находят свои операции. У заказов, начатых раньше, номера случайные.

Ошибки имеют единую форму:

```json
{"error":{"code":"validation_error","message":"Проверьте данные"}}
```

## Контракт предварительного расчёта

`quote-preview` принимает `vehicleId` и массив `selections` с элементами `{ type: "service" | "package", id }`. Цена услуги складывается из её операций для tenant-класса автомобиля. Сначала учитываются операции пакетов; совпадающие операции отдельных услуг возвращаются в `excludedOperations` и не прибавляются повторно.

Ответ содержит:

- `preliminary: true`;
- `lines` со снимком операций и режимом цены;
- `totalAmountMinor` и `totalDurationMinutes`;
- `warnings` для пересечений пакета и цен, уточняемых после осмотра.

`POST /api/bookings` повторяет расчёт на сервере и не доверяет сумме из браузера. `resourceId` может быть `null`: наличие выделенного бокса не является условием создания записи. Повтор идентичного запроса с тем же `Idempotency-Key` возвращает ранее созданную запись; другой payload с тем же ключом получает `409 idempotency_conflict`.

Если передан `leadId`, запись атомарно связывается с обращением, а обращение становится `CONVERTED`. Повторная конвертация и привязка обращения известного клиента к другому клиенту возвращают `409`.

`PATCH /api/bookings/{id}` доступен роли `admin` и изменяет только подтверждённую запись текущего tenant. Перенос повторно проверяет вместимость центра, исключая саму переносимую запись. Отмена сохраняет запись со статусом `CANCELLED`. После создания заказа запись блокируется для переноса и отмены с `409 booking_has_order`.

Доступные слоты генерируются из настроек центра: рабочих дней, времени открытия/закрытия, шага записи и одновременной вместимости. `POST /api/bookings` и перенос повторно проверяют график на backend, поэтому запись вне часов или между настроенными слотами возвращает `409 slot_unavailable`. Выделенные боксы для этого не требуются.

Для календаря `GET /api/bookings` принимает пару локальных дат `from=YYYY-MM-DD` и `to=YYYY-MM-DD`. Диапазон ограничен 31 днём и сортируется хронологически; без диапазона сохраняется обратная сортировка списка последних записей. Интерфейс предоставляет режимы «День», «Неделя» и «Список», при этом недельный режим показывает загрузку семи дней без предположения о наличии боксов.

Пересекающиеся отдельная услуга и пакет разрешены: оплачиваемые операции услуги уменьшаются на операции пакета. Два пакета с общими операциями возвращают `409 package_overlap`, поскольку без отдельной декомпозиции цены корректно распределить скидку невозможно. Занятый сверх вместимости слот возвращает `409 slot_unavailable`.

## Контракт редактора каталога

Редактор возвращает услуги и пакеты текущего tenant, в том числе архивные, а также тарифные классы центра. Изменение услуги обновляет цену и длительность каждой операции отдельно: это сохраняет корректное исключение операций, уже входящих в пакет. Пакет редактируется общей ценой и длительностью по классу.

Новая услуга создаётся из одной или нескольких tenant-scoped операций. Для каждой операции передаётся стартовая цена и длительность; они копируются на классы центра и затем редактируются раздельно. Новый пакет переиспользует ту же библиотеку операций и получает стартовую общую цену. Изменение `operationIds` меняет только будущие расчёты: существующие снимки записей и смет не переписываются.

Архивирование устанавливает `active = false`: позиция исчезает из новых записей, но существующие снимки записей и смет не меняются.

## Контракт разделов и простых услуг

Все маршруты требуют `manageCatalog` и действуют внутри центра.

**Разделы** (`catalog_sections`, миграция `020`) — упорядоченный список групп каталога. Позиция относится к разделу по своему `category`, поэтому данные переносить не нужно:
- раздел для уже используемой категории создаётся при первом чтении;
- переименование раздела меняет `category` у его услуг и пакетов, а снимки записей и смет сохраняют прежние названия;
- название уникально без учёта регистра;
- удалить можно только раздел без позиций, включая архивные;
- в каталоге для записи (`GET /api/tenants/current/services`) группы идут в порядке разделов.

**Цена по умолчанию.** Строка цены с `tenant_class = '*'` действует для любого класса автомобиля, у которого нет своей строки. Это касается и расчёта записи, и каталога для записи. Поэтому у центра без правил классификации услуги тоже работают. Для такого центра `vehicleClasses` в редакторе равен `['*']`, а стартовые цены составных позиций пишутся в эту строку.

**Простая услуга** — обычная услуга из одной операции, которую сервер создаёт сам с названием услуги. Отдельной сущности нет: запись, смета и работы мастера обходятся без особых случаев.
- `POST /simple-services` принимает `{ sectionId, name, description?, pricingMode, basePrice: { amountMinor, durationMinutes }, classPrices?: [{ tenantClass, amountMinor, durationMinutes }] }`.
- `basePrice` пишется в строку `*`, `classPrices` — только для классов центра.
- Активная операция с тем же названием переиспользуется. Если такая операция в архиве — `409 operation_archived`. Дубль активной услуги — `409 service_exists`. Нет раздела — `422 section_required`.
- `PUT /simple-services/{id}` дополнительно принимает `active` и полностью заменяет цены услуги. Для услуги из нескольких операций — `409 service_not_simple`.
- При переименовании скрытая операция получает новое название, если её не используют другие услуги и пакеты. Иначе она сохраняет имя, чтобы не переименовать чужие позиции.

В `GET /api/tenants/current/catalog` добавлены `sections`, а у услуг — `simple`, `basePrice` и `classPrices` (только отличия от базовой цены). Если у старой услуги все классы стоят одинаково, это одна `basePrice`. Если разные и без строки `*` — `basePrice: null`.

## Контракт библиотеки операций

Маршруты доступны ролям `owner`/`admin` (`manageCatalog`) в пределах центра. Операция другого центра возвращает `404 operation_not_found`.

- **Переименование.** Новое название применяется к будущим расчётам и каталогу. Записи (`booking_quote_lines`, `booking_quote_versions`) и сметы хранят снимок прежнего названия.
- **Архивация `active: false`.** Отклоняется с `409 operation_in_use`, пока операция входит хотя бы в одну активную услугу или пакет; `details` перечисляет их. Операцию, которая используется только в архивных позициях или не используется вовсе, архивировать можно. Архивную операцию нельзя выбрать в новой услуге или пакете.
- **Возврат позиции в продажу.** Услугу или пакет с архивной операцией в составе нельзя сделать активной: `PATCH …/services|packages/{id}` с `active: true` возвращает `409 operation_archived`.
- **Валидация.** Тело — только `name` (2–120 символов) и/или `active` (boolean). Иначе `422 validation_error`.

В поиске клиентов `visitCount` теперь означает число закрытых заказов клиента — то же значение, что `stats.closedOrders` в карточке. Колонка `customers.visit_count` не используется.

## Контракт команды

Сотрудник может совмещать несколько ролей центра: системных (`owner`, `admin`, `intake`, `master`) и своих (`role_<uuid>`, см. «Контракт ролей»). Принимаются только неархивные роли своего центра, иначе `422`. Роль QC не назначается новым сотрудникам, пока этап контроля качества депрекейтнут. Все списки и изменения tenant-scoped; управлять командой может только тот, у кого есть `manageTeam`, то есть роль `owner`.

При создании API один раз возвращает `accessToken`. В базе хранится только SHA-256-хеш токена. Роли активной сессии читаются из сотрудника при каждом запросе, поэтому их изменение действует сразу, а статус `blocked` запрещает дальнейший вход. Удалить роль владельца или заблокировать последнего активного владельца нельзя (`409 last_owner_required`). Email-приглашения, пароли и production-аутентификация в локальный контракт не входят.

## Контракт ролей

Владелец настраивает роли центра в «Команда → Роли и права». Права — фиксированный список, отдаётся в `permissions`:

`viewAnalytics`, `manageBookings`, `manageCustomers`, `manageIntake`, `approveEstimates`, `assignMasters`, `performWork`, `acceptAssignments` (исполнитель заказов: попадает в список мастеров и видит «Мои»), `closeOrders`, `manageCatalog`, `manageSettings`.

`manageTeam` в список не входит: это право есть только у роли `owner`.

| Роль | Права по умолчанию | Что можно менять |
|---|---|---|
| `owner` Владелец | все, кроме `acceptAssignments`, плюс `manageTeam` | ничего (`409 role_locked`) |
| `admin` Администратор | все, кроме `acceptAssignments` | права |
| `intake` Приёмщик | `manageIntake` | права |
| `master` Мастер | `performWork`, `acceptAssignments` | права |
| своя `role_<uuid>` | выбранные | название, права, архив |

Владелец, который сам выполняет работы, дополнительно получает роль с `acceptAssignments`. Название системной роли не меняется (`409 role_name_locked`).

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/tenants/current/roles[?includeArchived=true]` | `{ permissions, items }`; у роли `key`, `name`, `system`, `locked`, `archived`, `permissions`, `memberCount` |
| `POST` | `/api/tenants/current/roles` | `{ name, permissions }` → `201`; название 2–40 символов, хотя бы одно право |
| `PATCH` | `/api/tenants/current/roles/{key}` | `{ name?, permissions? }` |
| `POST` | `/api/tenants/current/roles/{key}/archive` / `restore` | Архив своей роли. Если роль есть хоть у одного сотрудника, в том числе заблокированного, — `409 role_in_use` |
| `GET` | `/api/tenants/current/roles/{key}/events` | Журнал: `ROLE_CREATED`, `ROLE_UPDATED` (было/стало), `ROLE_ARCHIVED`, `ROLE_RESTORED`, кто и когда |

Все маршруты требуют `manageTeam`. Название уникально в центре без учёта регистра, включая системные (`409 role_name_taken`). Права хранятся в `tenant_roles` (миграция `019`). Строка для системной роли появляется только после её правки; до этого действуют значения по умолчанию из кода. `tenant_members.roles_json` по-прежнему хранит ключи ролей, поэтому старые данные переносить не нужно. Права сессии пересчитываются на каждом запросе: правка роли действует сразу для всех её сотрудников. `GET /api/session` возвращает `actor.roleNames` и `capabilities.acceptAssignments`.

## Доступ на чтение по ролям

Права вычисляет сервер по ролям сотрудника. Скрытые в интерфейсе кнопки защитой не считаются. В колонке «Роли по умолчанию» указаны права системных ролей до правки владельцем.

| Данные | Нужное право | Роли по умолчанию |
|---|---|---|
| Поиск клиентов, автомобили клиента, поиск по госномеру, справочник моделей, карточки клиента и автомобиля | `manageCustomers` | admin |
| Обращения | `manageBookings` | admin |
| Список записей | `manageBookings` или `manageIntake` | admin, intake |
| Доступность слотов, предварительный расчёт, каталог по автомобилю | `manageBookings` | admin |
| Одна запись `GET /api/bookings/{id}` (без телефона), заказы | любая роль центра | все |

Отказ — `403 forbidden` с сообщением «Раздел недоступен для вашей роли».

`GET /api/tenants/current/masters` (`assignMasters`) возвращает активных сотрудников, чьи роли дают `acceptAssignments`, и их загрузку: `activeOrders` — заказы в статусах `APPROVED` или `IN_PROGRESS`, назначенные на сотрудника. `PUT /api/orders/{id}/assignment` принимает `{ memberId }`. Это должен быть активный сотрудник центра с `acceptAssignments`, иначе `422 not_a_master`. Связь хранится в `order_assignment_members`, а `masterName` остаётся снимком имени. Старый вариант `{ masterName }` без связи с сотрудником по-прежнему принимается. В заказе `assignment.memberId`, в списке заказов `masterMemberId`.

## Списки записей

`GET /api/bookings` принимает `view`:

- `view=upcoming` — записи с начала сегодняшнего дня по часовому поясу центра, ближайшие первыми;
- `view=overdue` — прошедшие записи `CONFIRMED` без заказа, по которым ещё не отмечены ни приезд, ни неявка; новые сверху.

Неизвестное значение `view` возвращает `422`. Без `view` сохраняется прежнее поведение (последние по времени начала) и диапазон календаря `from`/`to`. Интерфейс использует `upcoming` для «Ближайших визитов» и `overdue` для блока «Требуют отметки».

## Контракт неявки

`PATCH /api/bookings/{id}` принимает `{ status: 'NO_SHOW' }` наряду с `CANCELLED`. Правила:

- неявку можно отметить только для подтверждённой записи без заказа;
- только после времени начала записи, иначе `409 booking_not_started`;
- повторная отметка возвращает `409 invalid_booking_state`, а запись с заказом — `409 booking_has_order`.

Слоты занимают только записи в статусе `CONFIRMED`, поэтому неявка освобождает место. Начать приёмку по такой записи нельзя.

Открытие существующего заказа на рабочем экране идёт через `GET /api/orders/{id}` и доступно любой роли центра, включая мастера. `POST /api/orders` (создание при приёмке) по-прежнему требует прав приёмки.

## Контракт изменения состава записи

`GET /api/bookings/{id}` дополнительно возвращает `quoteVersion` (номер текущей версии расчёта) и `quoteVersions` (все версии по возрастанию: `version`, `vehicleClass`, `totalAmountMinor`, `totalDurationMinutes`, `reason`, `actorName`, `createdAt`, `lines`). Поле `lines` — строки **текущей** версии. Запись без изменений имеет одну версию `1`, собранную из исходного снимка.

`PUT /api/bookings/{id}/quote` (роль `admin`, `manageBookings`) принимает `{ selections, expectedQuoteVersion, reason? }`. Другие поля, включая клиента и автомобиль, отклоняются с `422 validation_error`. `reason` — до 200 символов. Сервер заново считает состав функцией предварительного расчёта по текущему каталогу и tenant-классу автомобиля записи; суммы из браузера не принимаются. Правила исключения повторно оплачиваемых операций и `409 package_overlap` такие же, как при создании записи.

Ошибки без частичных изменений:

- `409 booking_has_order` — по записи уже создан заказ, состав дальше меняется через смету;
- `409 invalid_booking_state` — запись не в статусе `CONFIRMED`;
- `409 stale_quote_version` — `expectedQuoteVersion` не совпадает с текущей версией;
- `409 vehicle_inactive` — автомобиль записи неактивен или продан;
- `409 quote_unchanged` — набор услуг и пакетов не изменился (случайный пересчёт по новым ценам каталога исключён);
- `409 slot_unavailable` — новая длительность не помещается в исходное время с учётом графика и вместимости центра; время записи не меняется автоматически;
- `404 offering_not_found` / `price_not_found`, `422 validation_error`.

Хранение: исходные `booking_quote_lines` никогда не изменяются. При первой правке они копируются в `booking_quote_versions` как версия 1 с исходными итогами и временем создания записи, затем добавляется новая версия. Все версии неизменяемы; в `bookings` обновляются только текущие `preliminary_amount_minor` и `estimated_duration_minutes`. Последующие изменения цен каталога не пересчитывают ни одну сохранённую версию. Ответ — обновлённая запись.

## Контракт заказа и сметы

`POST /api/orders` принимает подтверждённый `bookingId`. Одна запись порождает не более одного заказа в tenant: повтор возвращает тот же заказ с `200`. Новый заказ начинается в `INTAKE`.

`PUT /api/orders/{id}/intake` принимает `conditionSummary`, массив `findings` (`zone`, `severity`, `note`) и массив `recommendations` (`title`, `reason`, `priority`). После сохранения заказ переходит в `ESTIMATE_DRAFT`, а событие `INTAKE_COMPLETED` попадает в аудит.

Каждый `POST /api/orders/{id}/estimates` создаёт новый снимок строк и вычисляет итог на сервере. Старые версии не обновляются. Согласовать можно только `currentEstimateVersionId`; устаревшая версия возвращает `409 stale_estimate`. Решение требует `decision`, `method`, `source` и `responsible`. После `APPROVED` приёмку нельзя молча переписать (`409 invalid_order_state`).

При старте работ операции копируются только из согласованной версии сметы: мастер не может добавить платную работу через производственный API. Незавершённая операция возвращает `409 operations_incomplete`. После завершения всех операций заказ сразу готов к выдаче. Исторические записи QC сохраняются; старый поток с `qc_rework` доступен только в rollback-режиме. Доступ к назначению и работе проверяется по ролям серверной сессии.

Выдача принимает `responsible` и `note`, разрешена только из `READY`, переводит заказ в `CLOSED` и сохраняет `ORDER_CLOSED` в аудите. Учёт оплаты в продукт не входит.

## Контракт фото заказа

`POST /api/orders/{id}/photos` принимает `{ phase, kind, zone, dataUrl }`. `dataUrl` — base64 data URL `image/jpeg`, `image/png` или `image/webp` размером до 700 КБ после декодирования; клиент заранее уменьшает изображение. Фото приёмки (`phase: "intake"`) добавляются в статусах `INTAKE` и `ESTIMATE_DRAFT` ролью приёмки, фото результата (`phase: "result"`) — только в `READY` ролью выдачи. На заказ хранится не больше 20 фото.

Фото сохраняются в SQLite в `order_photos.data_url`; фото результата отмечаются в `order_result_photos` без копирования данных. Это решение локального прототипа, а не production-хранилище. Выдача без хотя бы одного фото «до» и одного фото «после» возвращает `409 handover_photos_required`.

## Контракт входа через мессенджер

Сотрудники входят без пароля через бота Telegram или MAX. Боты включаются переменными `TELEGRAM_BOT_TOKEN` и `MAX_BOT_TOKEN`. Сервер получает события методом long polling (`getUpdates` в Telegram, `GET /updates` в MAX), поэтому публичный домен и вебхук не нужны, достаточно исходящего HTTPS.

**Привязка.** Владелец вызывает `POST /api/tenants/current/team/{id}/messenger-invites` с `{ provider }` и получает одноразовый `code` (`invite_…`), `deepLink` и `expiresAt` (24 часа). Сотрудник открывает ссылку и нажимает «Старт» либо отправляет код боту. Бот привязывает его аккаунт к сотруднику: `member_messenger_links`, один аккаунт на сотрудника и мессенджер в центре. Чужой аккаунт, уже привязанный к другому сотруднику центра, отклоняется. `GET /api/tenants/current/team` возвращает у сотрудника `messengerLinks`.

**Первый владелец.** В новой установке войти ещё некому, поэтому первого владельца создают с консоли сервера: `pnpm setup:owner -- --center "Название" --owner "Имя"`. Команда создаёт центр без демо-данных и сотрудника с ролями `owner` и `admin`, а затем печатает приглашение для каждого настроенного мессенджера (или для указанных в `--provider`). Если владелец потерял доступ, `--tenant <id>` добавляет нового владельца в существующий центр. Центр с уже существующим названием не создаётся. Перед изменением снимается резервная копия. HTTP-маршрута для этого нет: доступ к консоли и файлу базы и так означает полный доступ.

**Вход.**

1. `POST /api/auth/login-requests` с `{ provider }` возвращает `id`, `pollSecret` (известен только браузеру), `shortCode` (6 символов), `deepLink` с одноразовым токеном и `expiresAt` (5 минут).
2. Сотрудник открывает ссылку или отправляет боту `shortCode`. Бот показывает тот же код и кнопки «Это я, войти» / «Отклонить». Не привязанный аккаунт получает отказ, статус не меняется.
3. Подтвердить или отклонить может только тот аккаунт, который открыл запрос. Статусы: `PENDING` → `AWAITING_CONFIRMATION` → `CONFIRMED` / `DENIED`; по истечении срока — `EXPIRED`.
4. Браузер опрашивает статус с заголовком `x-login-secret`. В статусе `CONFIRMED` видны `memberships` — центры, где аккаунт привязан к активному сотруднику.
5. `POST …/session` (при нескольких центрах с `{ tenantId }`, иначе `409 choose_tenant` со списком) выдаёт `token` (`dfs_…`, 30 дней) ровно один раз; затем запрос получает статус `CONSUMED`.

Секреты (`pollSecret`, токен ссылки, код приглашения, токен сессии) хранятся только как SHA-256-хеши. Сессия перестаёт работать после `POST /api/auth/logout`, блокировки сотрудника, отвязки этого мессенджера или по сроку. Роли и права по-прежнему вычисляются сервером из записи сотрудника.

Адаптер MAX собран по публичной OpenAPI-схеме MAX и покрыт тестами на записанных формах событий. Перед промышленным запуском его нужно проверить на живом боте: в официальной документации не все поля описаны текстом.

## Контракт документов заказа

Два типа документов:

- `intake_act` — акт приёмки. Доступен после сохранения приёмки (`409 document_not_available` до этого). Выпуск доступен ролям `admin`/`intake`.
- `handover_act` — акт выдачи (заказ-наряд). Доступен только для заказа в статусе `CLOSED`. Выпуск доступен роли `admin` (`closeOrders`).

Чтение, предпросмотр и список доступны при `manageIntake` или `closeOrders`. Заказ другого центра возвращает `404`.

`POST /api/orders/{id}/documents` принимает только `{ type, signerName?, signatureDataUrl? }`. `signerName` и `signatureDataUrl` передаются вместе или оба отсутствуют. Подпись — `data:image/png;base64,…`, проверяется сигнатура PNG, размер не больше 200 КБ, ФИО от 2 до 120 символов. Содержимое акта клиент не передаёт: его собирает сервер из состояния заказа на момент выпуска. Ответ `201` — документ целиком.

Каждый выпуск создаёт новую неизменяемую строку `order_documents` с номером по центру и типу: `АП-000001`, `АВ-000001`. Подпись никогда не добавляется к уже выпущенному акту: «подписать позже» означает выпустить новый номер. В списке последний акт каждого типа имеет `current: true`. Акт приёмки получает `outdated: true`, если приёмку пересохранили после его выпуска. Снимок при этом не меняется. Выпуск пишет в журнал заказа событие `DOCUMENT_ISSUED`. `GET /api/orders/{id}` дополнительно содержит `documents` (краткий список без изображений подписи).

Подпись необязательна и ничего не блокирует: выдача и закрытие заказа работают как раньше. Акт выдачи содержит работы из согласованной сметы, её версию и сумму, данные согласования и выдачи. Сведений об оплате в документах нет.

## Контракт карточки клиента

Все маршруты карточки доступны роли `admin` (`manageCustomers`) и ограничены tenant текущей сессии. Клиент другого центра возвращает `404 customer_not_found` для чтения и любых изменений.

`GET /api/customers/{id}/profile` возвращает:

- `customer`: `id`, `name`, `phoneDisplay`, `archived`, `archivedAt`, `createdAt`;
- `stats`: `bookings`, `openBookings` (подтверждённые записи без заказа), `orders`, `activeOrders`, `closedOrders`, `lastVisitAt`. Агрегаты считаются по фактическим записям и заказам; платёжных метрик нет;
- `vehicles`: автомобили по активным связям `CustomerVehicle` (включая неактивные и проданные) с `relationType` и `ownedFrom`;
- `formerVehicles`: закрытые связи клиента с `validFrom`, `validTo`, автомобилем и его текущим владельцем;
- `bookings` и `orders`: последние 20 записей и заказов, созданных на этого клиента. Заказ, созданный до передачи автомобиля, остаётся у прежнего клиента;
- `phoneDuplicates`: другие клиенты текущего центра с тем же нормализованным телефоном;
- `audit`: события `CUSTOMER_UPDATED`, `CUSTOMER_ARCHIVED`, `CUSTOMER_REACTIVATED` с `details`, `actorName` и `createdAt`, новые сверху.

`PATCH /api/customers/{id}` принимает только `name`, `phone` и необязательный `confirmDuplicate`. Имя — от 2 до 120 символов. Телефон нормализуется той же функцией `normalizePhone`, что и поиск, и должен содержать от 7 до 15 цифр. Неизвестные поля, пустое тело и неверные типы возвращают `422 validation_error` без частичных изменений. Если новый нормализованный телефон уже есть у другого клиента этого центра, ответ `409 possible_duplicate` содержит `details.matches`. Клиенты не объединяются и автомобили не переносятся. Повтор с `confirmDuplicate: true` сохраняет изменение и пишет в аудит `duplicateAcknowledged`. Изменение без фактической разницы не создаёт событие. Архивного клиента изменить нельзя: `409 customer_archived`. Успешный ответ — обновлённая карточка.

`POST /api/customers/{id}/archive` заполняет `archived_at` и пишет `CUSTOMER_ARCHIVED`. Связи с автомобилями, записи, заказы и обращения не изменяются. Если у клиента есть подтверждённые записи без заказа, незакрытые заказы или обращения в статусах `NEW`/`CONTACTED`, ответ `409 customer_has_active_work` содержит `details.confirmedBookings`, `details.openOrders` и `details.activeLeads`. Архивный клиент скрыт из обычного поиска и не может получить новый автомобиль, запись, обращение или автомобиль через передачу. `POST /api/customers/{id}/reactivate` снимает архив и пишет `CUSTOMER_REACTIVATED`. Оба действия идемпотентны и при повторе не создают новое событие.

## Контракт истории автомобиля

Профиль и изменение владельца доступны роли `admin` и всегда ограничены текущим tenant. Передача принимает только явный `customerId` существующего неархивного клиента: поиск по телефону или госномеру никогда не меняет связь автоматически. Повторная передача тому же владельцу возвращает `409 same_owner`.

В одной транзакции у прежней связи `CustomerVehicle` заполняется `validTo`, создаётся новая активная связь и записывается `OWNER_TRANSFERRED`. Исторические заказы не перепривязываются: в визите остаётся клиент, с которым заказ был создан. Статус `sold`/`inactive` управляется отдельно от владельца и также журналируется.

`POST /api/vehicles` принимает либо `catalogVariantId`, либо объект `manual` с явными `make`, `model` и `bodyType`. Ручной ввод не создаёт дубль глобального справочника. Для него указывается tenant-класс, который сохраняется отдельным override и имеет приоритет над системным правилом. Такой же override можно скорректировать через `PATCH /api/vehicles/{id}`; готовые расчёты не пересчитываются.

## Отличия от предложений исходной спецификации

- Пути основных ресурсов совпадают с предложенными. Первая связь `CustomerVehicle` создаётся атомарно вместе с автомобилем, а смена владельца опубликована отдельным явным маршрутом с аудитом.
- Ручное добавление отсутствующей модели, tenant-класс автомобиля и редактирование состава услуг реализованы.
- Фото приёмки и результата сохраняются в SQLite как data URL (`order_photos.data_url`) и обязательны для выдачи; отдельного объектного хранилища в прототипе нет. Акты приёмки и выдачи с необязательной подписью клиента на экране реализованы; печать и PDF выполняются средствами браузера. Это простая рукописная подпись на экране, а не квалифицированная электронная подпись. Учёт оплаты намеренно отсутствует.
- Карточка клиента не выполняет слияние клиентов и не удаляет историю: возможный дубль телефона только показывается, архивация — отдельное явное действие.
- Создание, редактирование и архивирование операций, услуг и пакетов реализовано; отдельное массовое управление библиотекой операций остаётся за границей текущего UI.
- SQLite и bearer-токены — локальная реализация прототипа; production-хранилище и существующая auth-система в исходном пустом репозитории отсутствовали.
